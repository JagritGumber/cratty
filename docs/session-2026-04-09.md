# Session 2026-04-09: Sidebar Fixes, Scroll Animation, Wispr Flow Support

## Issues Fixed

### 1. Sidebar "New workspace" button layout broken

**Symptom:** Plus icon took half the button, text took the other half.

**Root cause:** `new_ws_button()` in `sidebar.rs` used `centered_icon(ICO_PLUS, 10.0)` which wraps the icon in a container with `center(Length::Fill)`. Inside a `row![]`, `Length::Fill` splits available space evenly between the icon container and the text, creating a 50/50 layout.

**Fix:** Replaced `centered_icon` with an inline container using `width(Length::Shrink)` so the icon only takes the space it needs.

**Files:** `sidebar.rs`

### 2. Workspace context menu stuck open permanently

**Symptom:** Opening the three-dots menu, deleting a workspace, then creating a new one left the menu permanently open with no way to close it.

**Root cause:** Two problems:
- The menu button always sent `ShowWsMenu(idx)`. Clicking it again re-sent the same message rather than toggling. `HideWsMenu` existed in the message enum but was never emitted from any UI element.
- `close_workspace()` and `SwitchWorkspace` never cleared `ws_menu_idx`. After deleting a workspace, the index stayed set. When a new workspace landed at the same index, the menu appeared stuck.

**Fix:**
- `ws_item.rs`: Menu button now toggles: sends `HideWsMenu` if already open, `ShowWsMenu(idx)` if closed.
- `app_actions.rs`: `close_workspace()` clears `ws_menu_idx`.
- `app_update.rs`: `SwitchWorkspace` clears `ws_menu_idx`.

**Files:** `ws_item.rs`, `app_actions.rs`, `app_update.rs`

### 3. Pane scroll animation was not actually animating

**Symptom:** Switching focus between panes caused an instant jump with no visible animation, despite `ViewOffset` having animation logic.

**Root cause:** `scroll_to_pane()` was called on every focus change, which instantly jumped the iced scrollable to the final pixel position via `operation::scroll_to`. The `ViewOffset` animation ticked in the background via `tick_animations()`, but nothing ever read its interpolated `current()` value to drive the actual scrollable widget. The animation was completely disconnected from rendering.

**Fix:**
- Focus/move pane changes now call `viewport.animate_to(target_pixel_x)` instead of instant-jumping. The `from` position comes from `viewport.current()` so rapid keypresses animate smoothly from the current interpolated position.
- `tick_animations()` now returns `Option<f32>`. On each tick, if an animation was in progress, the handler scrolls the widget to the interpolated position.
- All instant scroll operations (`scroll_to_pane`, workspace switch, new pane) now sync `viewport` to `ViewOffset::Static(x)` so `animate_to` always has the correct starting position for future animations.
- Replaced the spring easing (`1-(1+8t)*exp(-8t)`, a=8) with `ease_out_quart` (`1-(1-t)^4`) and dt=0.07 for a snappier ~230ms animation.

**Key insight:** The original code animated between focus *indices* (0, 1, 2...) not pixel positions. The ViewOffset was never connected to the scrollable's actual pixel offset. Changing to pixel-based animation and driving the scroll on each tick fixed it.

**Files:** `view_offset.rs`, `app_tick.rs`, `app_update.rs`, `app_actions.rs`

### 4. Ctrl+V paste for Wispr Flow (STT) support

**Symptom:** Wispr Flow (speech-to-text tool) fails to paste in terminals including Alacritty and Tabby. It puts transcribed text on the clipboard and simulates Ctrl+V, but terminals send the raw control byte `0x16` to the PTY instead of pasting.

**Root cause:** The canvas event handler in `term_widget.rs` passes all Ctrl+letter combos to `key_to_bytes()`, which converts Ctrl+V to byte `0x16` (ASCII SYN). Only Ctrl+Shift+V triggered clipboard paste. Wispr Flow simulates plain Ctrl+V which never reached the paste logic.

**Fix:** Added an intercept in the canvas `update()` handler: when Ctrl+V (without Shift) is detected, emit `Message::PasteTerminal` via `canvas::Action::publish` instead of forwarding the raw byte. This makes Ctrl+V paste from clipboard, matching Windows Terminal behavior and enabling Wispr Flow support.

**Files:** `term_widget.rs`

## Easing function evolution

Started with critically damped spring (`a=8`), which was too aggressive (90% done in first 5 frames). Changed to `ease_out_cubic`, then the user said animation was still too slow/subtle. Final: `ease_out_quart` with dt=0.07 (~14 frames, ~230ms). The quart curve covers ~30% of distance in frame 1 and settles quickly.

## Wispr Flow research summary

Wispr Flow is an AI speech-to-text tool that injects transcribed text into any active text field using OS accessibility APIs. When accessibility injection fails (common in terminals), it falls back to clipboard + simulated Ctrl+V. Terminals fail because:
- They use raw keyboard event capture, not standard text input widgets
- Canvas/GPU renderers bypass the OS text input pipeline
- No IME or accessibility API support (iced itself lacks this: iced-rs/iced#552)

The Ctrl+V interception is the practical fix. Full accessibility support would require iced framework changes.
